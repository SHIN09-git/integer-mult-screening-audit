# 整数乘法成本核验：快速筛选何时省时

JIN HANZHE · Independent Researcher, Chongqing, China  
研究日期：2026-10-15；公开整理及复跑：2026-10-22

## 这项研究回答什么

在搜索整数乘法构造时，候选方案需要通过成本核验。精确计算可能较贵，先用较便宜的严格上下界筛掉必定不合格的候选，是否能缩短总耗时？

本项目给出一个可以完整复跑的实例：对同一份固定旧账单，能提前拒绝的目标确实省时；原本能通过或筛选无法判断的目标仍需完整计算，筛选会增加开销。因此，公开价值在于可检查的方法、反例和测量记录，不在于宣称所有整数乘法计算都提速。

## 固定对象与来源

旧账单来自 Dugongue 的 [PR #2260](https://github.com/CrocSwap/integer-mult-bounds/pull/2260)，固定提交为 `fde6b107e26a14da5bac5b66913c914708ea6901`。实验重新读取全部 72 次调用、每次 436 个辅助位置，共 **31,392 条位置安排**。重算结果为宽度 73、活跃容量 7,168、计费秩总量 520,704，对应原始缺口 `73 × 7168 − 520704 = 2560`。物理总量 7,745 只作原记录交叉核对，不据此声称重做了整个物理实现证明。

实验保留原费用模型和带继承附加费的保守模型。保守模型中的附加费进入全部相关矩量，不能只调整缺口而保留其余量不动。输入清单、原字节和完整算术结果均随包保存。

二次比较界来自 Aaron Wang / navinor 的 [PR #1669](https://github.com/CrocSwap/integer-mult-bounds/pull/1669)，固定提交为 `b910e86383b2270cf14b7b659a808fa0eb075c7d`。本项目应用既有定理，并直接在给定门槛处求值，省去寻找根区间所需的两次 100 步二分；没有将这个代入步骤当作新定理。

## 怎样提前拒绝，又怎样回退

上游将成本函数写成正系数指数和。已有二次包络提供严格的上下界：

- 下界已经大于 1，可以确定该门槛下成本过高，提前拒绝。
- 上界严格小于 1，可以确定这一个成本函数通过。
- 包络跨过 1，或恰好碰到边界，则暂时无法判断。

公开实现只在**严格证明应当拒绝**时提前返回。其余情况，包括筛选已经给出成本通过的情况，仍运行 Mercator 与 atanh 两套完整精确计算。这样，“筛选无法判断”不会被误当作“接受”，通过的候选也不会跳过既定精确核验。

所有判断使用保留的有理数或有保证的有理区间。展示的十进制数只用于阅读；本项目不把二次根区间冒充精确到某个极细网格的根证书。

## 门槛如何选择

主分析使用四种门槛及两种费用模型，共 8 个组合：原选定参数换算值、旧方案宣称的复数指数节省值 `8417/5000000 = 0.0016834`、人为提高的门槛、以及筛选根区间中点。人为提高的门槛便于检查提前拒绝，但不能代表真实候选分布。

补充分析采用 [PR #2284](https://github.com/CrocSwap/integer-mult-bounds/pull/2284) 固定提交 `e71574b92f6af546013c71293cd03ff58742a1e6` 中的更高目标 `84179/50000000 = 0.00168358`，在两种费用模型下各检查一次。这个目标是在首轮计时之后找到的公开比较对象，属于事后补测。

补测始终使用 **#2260 的旧账单**。#2284 自身改进后的新账单没有被替换进来，也没有被本项目否定。#2284 原记录已指出旧账单不能满足这个目标；本项目研究的是在该例上筛选和精确回退的耗时，并非首次发现旧方案不够好。

## 历史结果与本次复跑

历史证据来自 2026-10-15 的 Windows / CPython 3.12.10。本次在 2026-10-22 的 Windows 11 / CPython 3.12.14 上重新生成一套计时。每套均包含 **581 个新启动进程**：350 个初始组合样本、168 个相邻配对样本及 63 个三方法比较样本。两套记录分别保存，没有混合汇总。

下表是较高公开目标、保守费用模型下的 21 组比较。百分比先在每组计算，再取中位数；不能直接用两列总耗时中位数相除来代替。

| 日期与方法 | 算术中位耗时 | 总耗时中位数 | 相对两套完整精确计算的配对节省 |
| --- | ---: | ---: | ---: |
| 历史：两套完整精确计算 | 61.21 ms | 339.42 ms | 基线 |
| 历史：原二次筛选 | 12.32 ms | 288.20 ms | 15.09% |
| 历史：直接门槛筛选 | 9.19 ms | 286.78 ms | 14.97% |
| 本次：两套完整精确计算 | 61.98 ms | 327.34 ms | 基线 |
| 本次：原二次筛选 | 12.27 ms | 274.97 ms | 16.01% |
| 本次：直接门槛筛选 | 8.89 ms | 273.43 ms | 16.10% |

这两个日期的较高目标比较中，两种筛选各自均在 21/21 组中快于两套完整精确计算。直接求值减少了算术部分耗时，但现有总耗时数据不足以把它与原二次筛选之间的小差别推广为稳定优势。

不能只看拒绝成功的情况。下表比较安全回退流程与两套完整精确计算；负的“节省”表示增加耗时。

| 保守模型情况 | 历史配对节省中位数 | 本次配对节省中位数 | 本次筛选流程更快的组数 |
| --- | ---: | ---: | ---: |
| 原宣称目标，成本通过 | −1.90%（增加 8.92 ms） | −4.26%（增加 14.72 ms） | 5/21 |
| 人为提高目标，可提前拒绝 | 14.41% | 15.23% | 21/21 |
| 根区间中点，需回退 | −1.52%（增加 6.51 ms） | −3.13%（增加 11.45 ms） | 4/21 |
| 人工混合四目标批次 | 4.47% | 2.55% | 15/21 |

基线选择也很重要。历史首轮在原目标下，原二次筛选的算术中位耗时约 15.50 ms，直接门槛求值约 11.19 ms，而**已有的单套 atanh 完整计算约 11.92 ms**，两套合计约 74.72 ms。不能据此宣称筛选总是比最快的单套完整计算更快；这里的主要收益比较对象是保留两套完整核验的流程。

## 计时能说明到哪里

总耗时计入子进程启动、来源及文件校验、输入读取与解压、全部位置安排重算、导入及算术。各进程独立启动，但没有清空操作系统文件缓存。历史首轮还保留了试运行产生的 Python 字节码缓存，随后配对补测前才移除；原始过程说明保存在 [BENCHMARK-PROVENANCE.json](../study/BENCHMARK-PROVENANCE.json)。

这些结果来自一份固定账单、少量选定门槛和当前机器负载，不能估算真实搜索中坏候选的比例、整场搜索收益或整数乘法算法运行时间。没有给出总体置信区间，也没有声称预注册、独立外部复现或完整定理证明。

## 可以实际核查什么

默认入口重新核验 31,392 条位置安排、10 个模型与门槛组合、17 项语义控制、12 项继承控制、4 项故意篡改检查，并比对完整原算术记录及其中 47 条外层严格不等式。回退检查观察实际精确计算调用，避免只相信程序自行填写的调用次数。

这些检查覆盖固定输入的来源、算术判断和回退行为；“成本通过”不能代替底层线路、精度、空间安排及任意规模推广的全部证明。本项目没有得到新的整数乘法复杂度上界。
